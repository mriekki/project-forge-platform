## Evidence examples

Record evidence only when the human explicitly chooses to update learning progress. Useful evidence can include:

- completed `/code-walkthrough` of a real implementation change set;
- explained the functional and technical purpose of important changed files;
- traced a request/data/state/event path across the implementation;
- explained a design choice and a credible alternative;
- reasoned through a failure mode or debugging approach;
- predicted then explained query-plan/index behavior using `/db-lab` evidence;
- explained schema/ORM/migration consequences from `/db-lab changes <work-item>`;
- traced an evidence-backed runtime/dependency path using `/system-lab`;
- predicted failure propagation, bottlenecks, consistency behavior, or latency consequences and reconciled the prediction with evidence;
- defended an architecture choice against a simpler credible alternative;
- adapted a design after an interview-style scale/reliability/security constraint changed;
- passed a `/learning-review` question at a demonstrated level;
- completed a focused `/coach` exercise or drill.

For database and system-design depth, prefer recording the demonstrated competency rather than one broad level. For example, capacity estimation, distributed consistency, API design, relational modeling and query-plan reasoning can legitimately be at different levels.

A walkthrough, generated workbench, or completed lab invocation is evidence of learning/review activity, not automatic proof of mastery. Record demonstrated understanding conservatively.

Do not update automatically.
