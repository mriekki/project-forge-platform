# Native-source release receipt v2 — dormant contract

This is a nonpublishing compatibility contract, not an accepted release, signature, registry request, or source authority transfer. No v2 receipt is installed under release/receipts; the checked-in historical v1 records and legacy live reader, stable descriptor and OIDC publisher remain unchanged.

## Contract

- `schemaVersion: 2`, `kind: project-forge-native-source-release`, exact stable package version, exact public Platform source.
- `source`: mode native-monorepo, exact source commit, previous accepted release version and exact previous receipt SHA-256, manifest SHA-256 and qualification event. Only immutable source identifiers, never private repository locators.
- Five component records with 40-character revision, explicit original-owner-git-commit or private-monorepo-git-commit kind and independently derived mappedInputSha256; Core retains its compatibility version. When mapped digest is unchanged, preserve the previously accepted component record, including its kind. Changed mapped content must have a distinct exact selected native commit; never replace every component identity on each release. Source ancestry and actual input hashes are independently verified in the source owner's tooling, not by converting receipt hashes to Git commits.
- Exact nativeSourceMain and platformMain successful run and attempt evidence. Do not fabricate original owner CI records for a native release.
- Retain existing exact archive SHA-256, npm registry shasum, verified neutral smoke, public OIDC publication run and signed Sigstore provenance reference. These are observations from actual authenticated/verified workflows, not authority claims derived from preview JSON.

The new module `scripts/native-source-receipt.mjs` constructs and validates strict structured records and compares them to independently obtained observations. It does not verify GitHub REST transport, npm signature, actual archive or registry status itself, write any receipt, grant publication, or choose a new source commit. The caller must do those checks independently, including previous receipt authenticity and mapping/source ancestry. Validation rejects unknown nested fields, unknown kinds, unchanged-input identity churn, wrong hashes or attempt, duplicate/non-advancing version and failed/incomplete CI or signed-publication evidence. Recovery classification separates missing, unknown and conflicting registry observations and prevents inferring republish permission from an interrupted receipt write.

## Live adoption work remains explicitly gated

The legacy receipt reader is intentionally not broadened by this dormant implementation. Existing alignment, candidate handoff, receipt read/CLI, release preparation, old-owner checkout, stable descriptor publication and recovery paths retain v1 behavior. Before activation: audit and implement explicit version dispatch and privacy-safe v2 output across all live consumers; verify a general native assembler against reviewed manifest and independently read bytes; authenticated prior-release continuity and source/main/full qualification; platform exact-public-main CI; actual generated/adopted consumer upgrade, managed drift refusal and rollback; publish/recovery simulation with real signed-proof requirements; verify final stable alignment after an authorized publication. No historical receipt changes, new signing system, npm trust root changes, credential changes or automatic source ownership transfer.

Fixtures exercise semantic continuity across successive native candidate revisions, full v1 backward compatibility in the unchanged reader, negative shape/identity cases, and ambiguous publication recovery. Tests use fabricated fact records and are not evidence of actual publication. Existing PR CI executes the tests. No new job or recurring cost.

## Separate prepublication intent and recovery

The nonauthorizing native release intent v1 binds exact package version, public source, private source commit, independently computed manifest digest, full prior receipt SHA-256, component revision kinds/digests, source and public CI run/attempts, and exact rebuilt candidate SHA-256. It has no actual-publication claims and hard-false authority fields. `verifyNativeIntent` compares the selected intent to independent observations and authenticated prior acceptance supplied by the caller. Later, and only after authorized publication and actual registry/signature/smoke verification, `constructNativeReceiptFromIntent` binds complete publication facts to that immutable intent. Recovery starts from the intent, not a hypothetical signed receipt. Unknown registry state blocks; absence grants no permission; an already matching archive must be verified without republishing; conflicting package/archive/receipt blocks. A matching receipt still requires live alignment verification. None of these pure library operations grants a write. The existing public issuer and its live workflows remain disabled for this source mode. All new records here are dormant fixtures, not releases.

## Exact prior receipt projection

The dormant `scripts/prior-release-projection.mjs` adapter selects prior receipt bytes by reviewed version and exact SHA-256. It explicitly dispatches v1/v2 and verifies the independently obtained package/source/artifact and component compatibility observations. For the initial five-component 4.35.0 migration it combines historical original revisions with separately recomputed mapped-input digests; v1 itself never claims those digests. For v2 it requires all computed digests to match and carries the recorded revision kinds forward. No unknown receipt fields are projected. The adapter joins the prior projection to the existing intent verifier; it makes no claim to authenticate GitHub transport, prior registry/signature checks, source mapping observations or the intent itself. Those must be supplied by a future separately reviewed protected transport and independent rebuild. No live receipt loader, publisher or stable alignment change. Tests use exact checked-in historical receipt bytes and synthetic independent observations, not a real new publication.

## Dormant stable contract alignment

The separate `scripts/native-release-contract-alignment.mjs` adapter compares a reviewed stable descriptor against exact receipt and npm archive bytes and independently obtained registry/source observations. It reuses the v1/v2 prior archive verifier (the accepted five-component 4.35.0 baseline and native v2 successors), validates descriptor version and selected profile, and requires that profile to exist in the verified archive's own component inventory. The profile must contain Core and Deployment and no duplicate or unknown components. The legacy stable alignment command, current descriptor, active publisher, and all historical receipts remain unchanged. A matching result does not authenticate the receipt, prove descriptor document hashes, reverify a Sigstore signature, or authorize alignment/publication; those remain independent protected release gates. Tests use disposable registry archive and receipt fixtures, including simulated native publication facts, not a new published release.
